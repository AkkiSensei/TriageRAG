# TriageRAG — Deep Audit & RAG-Showcase Roadmap

> **Research prototype. Synthetic data only. Not a medical device. Not for clinical use.**
> Snapshot audited: `TriageRAG.zip` (CHANGELOG `0.2.1`, 2026-10-29). Report date: 2026-10-29.
> Companion files: `TriageRAG_Rule_Catalogue_v1.md` (≈110 candidate rules + data lists) and `test_audit_regressions.py` (failing-first tests for the engine bugs below).

---

## 0. Executive summary

**One-paragraph verdict.** TriageRAG is an unusually disciplined *safety-engineering* prototype: fail-closed semantics, honest provenance flags, layer isolation, mutation testing, an audit chain, and ADRs. As a **Retrieval-Augmented Generation demonstration**, however, it is currently weak, and in places its own metrics overstate what has been shown. The knowledge base is tiny (12 rules, 8 drugs, 27 protocol chunks), the headline retrieval score (100% Recall@5) is achieved by a **random ranker** (measured, §3.2), the "dense" and "rerank" arms contain no neural model, and the generation side has only ever run against a scripted fake LLM. Underneath, I found **three latent engine defects that can let a contraindicated or mis-dosed step through** (confirmed by running probes; two are currently masked by a redundant rule).

**Good news:** every problem found is fixable inside the existing architecture, and the fixes make the project *more* impressive, not less. The strongest version of this project is not "a bigger rule list". It is **"a RAG system whose claims are falsifiable"**: a real corpus, a benchmark that a random ranker cannot pass, real models, and a pipeline that uses retrieval to *source and explain the rules themselves*.

## 2. What is genuinely strong (keep, and say so in the README)

1. **Fail-closed by construction** — tri-state `Measured`, `UNVERIFIED` as a first-class verdict, qualified wording ("CHECKED CLEAR (ruleset coverage: N)"), and the UI refusing to print a bare "CLEAR".
2. **Provenance honesty** — everything the agent authored is `PLACEHOLDER_UNRETRIEVED` / `verified: false`; vitals flags with no source emit *nothing*. This is the behaviour reviewers look for and almost no student project has it.
3. **Hard BLOCK lockout** with a `PermissionError` path and an AST/rule conformance test (R11).
4. **Layer isolation enforced in CI** (import-linter) and offline-by-default tests (socket guard).
5. **Prompt-injection posture** — complaint text excluded from retrieval/LLM by default; retrieved chunks sanitized and delimited; 32 adversarial attacks.
6. **Audit chain** with file locking and a concurrency test.
7. **Statistical habits** — bootstrap CIs, dev/test split, a codified `decide_backend()` rule, calibration reporting, and *disclosed* weak results (0% vitals-only Recall@1 under HD-1).
8. **Governance artefacts** — ADRs, `HD-*` human-decision register, `BACKLOG` ordered by safety priority.

The problem is not rigor; it is that rigor is currently being applied to a corpus and benchmark too small to test anything.

## 3. Findings

### 3.1 Engine and safety defects

#### ENG-01 (S0) — Confirmed trigger downgraded to a skip
`rule_engine.py`, `ClassInteractionRule` lookback loop. For each PDE5 med the loop sets `lookback_missing_timestamp` when `last_dose_time is None` (then `break`s only the inner loop), and later checks `if lookback_missing_timestamp: return SkippedCheck` **before** `if lookback_triggered: return Alert`.
**Probe A:** sildenafil taken 3 h ago + tadalafil with no timestamp + proposed nitroglycerin → class rule `DDI_PDE5_NITRATE` returns a *skip*, not BLOCK.
**Why it survived:** the redundant pair rule `DDI_SILDENAFIL_NITROGLYCERIN_EXPLICIT` still fired and masked it (see ENG-09).
**Fix:** evaluate all meds first; a confirmed in-window trigger **always** wins (BLOCK), and only if none triggered and some timestamp is missing → skip. Better: model time-since-last-dose as an interval `[lo, hi]` (unknown = `[0, ∞)`); within-window is TRUE if `hi ≤ limit`, FALSE if `lo > limit`, else UNKNOWN → fire as `POSSIBLE` (conservative) rather than skip.

#### ENG-02 (S0) — Baseline de-duplication hides proposed-drug coverage
`evaluate_plan` drops a plan alert when `any(ba.rule_id == alert.rule_id for ba in baseline_alerts)`. The step verifier decides strike-through by intersecting the step's drug with `alert.drug_ids`.
**Probe C (redundant rule removed):** home sildenafil + home isosorbide mononitrate fires `DDI_PDE5_NITRATE` at baseline with `drug_ids=[isosorbide_mononitrate, sildenafil]`; proposed nitroglycerin then produces no new alert → `nitroglycerin` appears in **no** alert → step is not struck through.
**Fix:** de-duplicate on `(rule_id, frozenset(drug_ids), origin)`; or never de-duplicate, and merge `drug_ids` instead. Add the property "adding a proposed drug can never remove an existing alert or shrink coverage".

#### ENG-03 (S0) — Dose results computed but ignored
`verify_dose` returns `BELOW_MINIMUM` / `MAGNITUDE_WARNING`; `evaluate_plan` only converts `EXCEEDS_CEILING` into an alert; `verify_plan` only acts on `EXCEEDS_CEILING` and `UNVERIFIED_MISSING_CAP`.
**Probe:** adult epinephrine IM 0.03 mg (×0.1 slip) → `BELOW_MINIMUM`, tripwire `True` → no alert, no step flag → step can be `APPROVED`.
**Fix:** map every non-`OK` status to a step status and alert (`DOSE_BELOW_MIN` MODERATE/HIGH by drug criticality; `DOSE_MAGNITUDE` HIGH). Add a test asserting *every* `CalculatedDoseReport.status` value has an explicit handling branch (exhaustiveness test).

#### ENG-04 (S1) — Gross overdose is only HIGH, hence overridable
**Probe:** 50 mg IM epinephrine (~100× ceiling) → `EXCEEDS_CEILING` → `DOSE_LIMIT_*` severity HIGH → step `FLAGGED_HIGH`, overridable with a 15-character rationale. README says "Absolute BLOCK… zero override code path" without this qualification.
**Fix (needs human decision HD-6):** define a *hard ceiling multiple* (e.g., requested > k × ceiling, or tripwire true) → BLOCK, non-overridable; keep HIGH for modest excess.

#### ENG-05 (S1, by inspection) — Dose reports keyed by `drug_id`
`dose_by_drug = {r.drug_id: r for r in dose_reports}` in `verify_plan`. Two administer steps for the same drug (e.g., repeat epinephrine) collide; the last report wins, so the first step may be judged by the second step's dose.
**Fix:** key by step index; add a two-step-same-drug test.

#### ENG-06 (S1) — The "dose engine" is a per-dose ceiling check
- `daily_max` is applied as an **absolute cap on the per-dose ceiling** (`calc_max = min(per_dose_max × weight, daily_max)`); there is no frequency, interval, cumulative-24 h, infusion-rate or volume logic. The name is misleading and the unit is wrong in data (ceftriaxone paediatric: `unit: mg/kg`, `daily_max: 2000` meaning absolute mg).
- `concentrations:` exists in the formulary YAML (e.g., epinephrine 1 mg/1 mL) and is **never used**; `CalculatedDoseReport` has no volume field. The concentration hazard (1:1000 vs 1:10 000, U-40 vs U-100 insulin, 1 000 vs 5 000 units/mL heparin) is therefore unrepresentable.
- Requested units other than mass or mass/kg (mL, mEq, units, mcg/kg/min) fall into `UNVERIFIED_MISSING_CAP` ("unit conversion failed") — fail-closed, but it means most real orders cannot be verified.
**Fix:** schema v2 dose rules: `per_dose`, `per_day`, `interval_h`, `max_rate`, `concentration_options`, separate absolute vs per-kg caps, volume computation, and cumulative checks across home meds with known doses.

#### ENG-07 (S2, by inspection) — Skips before applicability
`_evaluate_single_rule` checks `requires_fields` (history incomplete, unresolved med/allergy, pregnancy unknown) **before** checking whether the rule's drugs/classes are even present. One unresolved medication therefore emits a skip for *every* rule that lists `medications`. Result: noisy "Skipped checks" lists and alert fatigue as rules grow.
**Fix:** relevance-gate first: emit a skip only when the rule *could* apply (a trigger side is present, or possibly present because history is incomplete). Report a single global "history incomplete" banner for the rest.

#### ENG-08 (S1, latent) — In-class drug without a lookback entry passes silently
If a class member is not in `lookback_hours_by_ingredient`, the loop matches nothing and the rule returns neither alert nor skip (**failing test confirms**). It is dormant today because the class has only two members; it triggers the moment you add vardenafil/avanafil (catalogue CV-01) without a lookback entry.
**Fix:** treat "class member present but no lookback entry" as skip (or conservative alert); add a data-lint rule: every class member referenced by a lookback rule must have an entry.

#### ENG-09 (S1) — Redundancy masks defects; tests share the author's blind spots
`DDI_SILDENAFIL_NITROGLYCERIN_EXPLICIT` duplicates the class rule and hid ENG-01/02. 213 tests, 65 golden cases and 51/51 mutants all passed anyway because (a) golden/mutation runs use the **full ruleset**, and (b) mutants are written by the same agent that wrote the code.
**Fixes (cheap, high-value):**
1. **Rule-isolation harness:** run every golden case against *only* the rule under test (`only_rules()` helper in the supplied tests).
2. **Differential testing:** write a ~100-line *reference interpreter* of the rule semantics (independent, deliberately naïve) and compare it with the production engine on Hypothesis-generated patients. This would have found ENG-01/02/08.
3. **Metamorphic properties:** alert-set monotonicity when adding proposed drugs; invariance under med reordering and brand↔generic swap (you have two of three).
4. **Mutate redundant rules** (remove one of a redundant pair; the golden suite should still pass — if not, the pair is load-bearing).

#### ENG-10 (S2) — The schemas cannot express most real rules
Missing from `Patient`/rules: comorbidity/condition tags (asthma, AV block, G6PD deficiency, peptic ulcer, suspected dengue…), lab values (eGFR, K⁺, INR, QTc, platelets, bilirubin), gestational age, route and concentration on plan steps, infusion rate, `severity_by_context`, separate baseline vs plan severity, `on_indeterminate` policy, evidence links. Rule types are limited to six (pair, class_interaction, allergy_crossreactivity, vitals_interlock, population, duplication), and `PopulationRule` is drug-specific. This is the real reason the rule count is 12. See §5.2.

#### ENG-11 (S2) — Inconsistent trust policy
Vitals-flag rules with `status: ACTIVE` *must* have `verified: true` (validator), so unsourced thresholds are inert; clinical rules and dose limits are `ACTIVE` while `verified: false` and **do** fire/gate. Both are defensible, but the difference is undocumented and unexplained in the UI. Define one policy (suggest: `trust_mode = strict | demo`; strict loads only VERIFIED; demo loads all and shows "N of M items verified" on every report).

#### ENG-12 (S2) — Orphan and drug-specific population rule
`POP_LISINOPRIL_PREGNANCY` is drug-specific, and `lisinopril` has no formulary entry (so a *proposed* lisinopril is rejected as an unknown formulary agent regardless). Convert to a class rule (`RAAS_INHIBITORS` + pregnancy) and add the drugs.

#### ENG-13 (S2) — Policy question on BLOCK for unknown reaction type
`ALLERGY_PENICILLIN_CEPH_R1_SIMILAR` is BLOCK for `reaction_types: [anaphylaxis_ige, unknown]`. A non-overridable block on an *unknown* reaction type is the most conservative choice but, in real settings, penicillin "allergy" labels are frequently unverified. Needs a clinician decision (suggest HIGH-with-override for `unknown`, BLOCK for documented anaphylaxis). Taxonomy is also thin: no angioedema, non-IgE delayed reactions, or intolerance-vs-allergy distinction (`mild_rash`/`gi_upset` currently trigger nothing).

### 3.2 RAG substance and evaluation integrity

#### RAG-01 (S1) — The corpus cannot exercise retrieval
Counted from `ingest_protocols()`: **6 documents, 27 chunks (6 parents + 21 child decision nodes), 725 words of protocol text**; 23 adult, 4 paediatric chunks, **no neonate document**. Only seven drug IDs occur across all drug-action annotations — exactly the 8-drug formulary the protocols were co-authored with. The text states by design that it contains "NO numeric doses" (R9), so retrieval is never tested on the content that matters most clinically (doses, thresholds, tables). The protocols were authored by the same agent in the exact `IF … THEN` grammar the chunker is built around → circular.

#### RAG-02 (S1) — The headline benchmark cannot fail (measured)
After the hard syndrome + population filter, **4–6 candidate chunks remain** and the metric is Recall@**5**. I simulated a random ranker over the 146 cases that expect a protocol (2,000 shuffles each, candidate sets from the real index):

| Ranker | Recall@5 (any relevant in top-5) | Top-1 relevant |
|---|:--:|:--:|
| Random order | **1.000** | **≈0.59** |
| Reported BM25 | 1.000 | — |

So "100% Recall@5" carries **zero evidence** that retrieval works. Additional weaknesses: only 21 distinct target chunks across 224 cases (the whole set of child nodes), all cases labelled `AGENT_AUTHORED_UNREVIEWED`, dev/test split by *query* not by *document* (so test queries target chunks seen in dev), and the "permutation sanity check" only proves scores are not constant. The honest disclosure of the 0% vitals-only result is to the project's credit — but the benchmark must be rebuilt so the same honesty applies to the positive results.

#### RAG-03 (S1) — Retrieval is routing, not search
A syndrome is required; the free-text complaint is deliberately excluded (R7); vitals-only queries abstain (HD-1). With a controlled-vocabulary syndrome in hand, "retrieval" is a metadata lookup over 4–6 items. The genuinely hard and valuable RAG problem — *given a clinician's question or an unstructured presentation, find the right protocol/evidence in a large corpus* — is out of scope by construction. This is a defensible *safety* choice for the plan-drafting path; it is the wrong choice for the project's *RAG showcase* unless additional retrieval surfaces exist (§4.3).

#### RAG-04 (S1) — No semantic retrieval anywhere
`CharNgramRetriever` (exposed as `dense`) is sparse character-n-gram TF; `LexicalOverlapReranker` is token overlap. The four-arm ablation therefore compares four lexical methods on a 27-chunk lexically homogeneous corpus and (correctly, mechanically) selects BM25. It says nothing about dense/hybrid/cross-encoder retrieval. Do not call these arms "dense" or "rerank" in the README until a neural embedding model and cross-encoder are present (HD-5).

#### RAG-05 (S2) — Ingestion handles only the project's own grammar
`ingest_protocols` globs `*.md` and the chunker's round-trip invariant assumes numbered `IF/THEN` nodes. There is no PDF/HTML parsing, table preservation, flowchart handling, or section-aware label chunking. Backlog item 4 ("real guideline ingestion") is therefore structurally blocked, not merely unscheduled.

#### RAG-06 (S2) — Rules and protocols are unlinked
Rule provenance is a placeholder string, not a pointer to a retrievable chunk. Alerts do not show *why* in the source's own words; protocols are not cross-checked against rules until plan time. Linking them (rule → evidence chunk, alert → label quote) is both the best safety UX and the best RAG demonstration available to this project (§4.6).

#### RAG-07 (S2) — No Indian-context retrieval or aliases
14 aliases: Viagra, Revatio, Cialis, Nitrostat, Lopressor, Toprol-XL, Amoxil, Ventolin, EpiPen ×3, Augmentin, Lopressor-HCT, and a bare "penicillin". None of Dolo, Crocin, Combiflam, Ecosprin, Deriphyllin, Asthalin, Pan-D, etc. The original motivation (Indian ER, brand FDCs, °F temperatures, Hinglish) is absent from the data.

#### RAG-08 (S2) — Citation support is lexical
Verbatim substring checking is strong. The overlap threshold (documented as ≥ 0.08) plus drug/action-cue binding prevents many failures, but semantic entailment (does the quoted span actually support *this step's* claim?) is unmeasured. Add a claim-level support evaluation with a human-labelled calibration set.

#### RAG-09 (S3) — Calibration on synthetic labels
ECE/threshold calibration on agent-authored labels is fine as an *observational* metric (as BACKLOG HD-3 already says); do not present it as evidence of clinical calibration.

## 4. Target design: "RAG you can falsify"

### 4.1 Principles
1. **Every claim has a baseline that could have beaten it** (random, BM25, no-retrieval, oracle-retrieval).
2. **Benchmarks must be able to fail:** a validity self-test fails CI if a random ranker scores above a threshold.
3. **Retrieval must be *necessary* somewhere in the product,** not merely present.
4. **Rules are evidence-linked:** each rule points at retrievable source chunks; each alert can show them.
5. **Numbers in docs are generated, never typed.**
6. **Keep the safety posture:** the LLM never decides; every new retrieval surface returns *cited text*, never orders.

### 4.2 Three stores and one link graph

```
 Protocol corpus (guideline text)  ──┐
 Evidence corpus (drug labels)     ──┼──►  chunk store (one schema, one index, license-tagged)
 Rule store (structured, YAML)     ──┘            ▲
        rule.evidence = [chunk_id, quote, sha]    │   alerts show the quote; Q&A cites it;
        alert → evidence chunks                   │   rule mining proposes rules from it
```

**Corpus tiers**

| Tier | Content | License posture | Size target |
|---|---|---|---|
| T0 | Current synthetic protocols (keep as regression fixtures) | own | 27 chunks |
| T1 | **Synthetic protocol generator**: ≥40 syndromes, templated + paraphrased + deliberately confusable (adult vs paediatric versions, superseded versions, near-duplicates, distractor sections). Labeled SYNTHETIC; used to test retrieval *mechanics* at scale | own | ≈600 chunks |
| T2 | **Drug-label evidence corpus** from openFDA `drug/label` for the ≈150 generics your catalogue needs; chunked by label section (Contraindications, Warnings, Drug Interactions, Use in Specific Populations, Dosage & Administration) | openFDA states its content is public domain under CC0 "unless otherwise noted" and warns some third-party content may not be — check each record; see https://open.fda.gov/terms and /license | ≈1.5–3k chunks |
| T3 | **1–3 real open guideline documents** (e.g., WHO emergency/paediatric materials). ### 4.4 Retrieval stack specification
- **Chunking:** section-aware for labels (use SPL section structure); heading-aware for guidelines (pymupdf4llm/Docling → Markdown, tables kept intact as one chunk with caption); decision nodes for flowcharts via a human-transcribed `decision_graph` YAML (OCR of flowcharts is unreliable; transcribe the 5–10 charts you care about). Parent–child retained.
- **Contextual headers** (already in `indexed_text`): extend with drug name + section type for labels; evaluate with/without as an ablation.
- **Dense:** one small open embedding model behind the existing `Retriever` protocol (HD-5: choose and record the license; candidates such as BGE-small, MiniLM, E5-small — verify each licence). Store vectors with a thin `VectorStore` interface (in-memory NumPy default; optional Qdrant/Chroma adapter).
- **Fusion:** RRF over BM25 + dense (already implemented for char-n-gram; re-point to neural).
- **Rerank:** cross-encoder (optional extra) behind the existing reranker protocol.
- **Query handling:** acronym/synonym expansion (exists), multi-query rewriting for R-3 via LLM *or* a deterministic rewriter, Hinglish/brand→generic normalisation via the alias layer.
- **Metadata filters:** population (hard, exists), syndrome (hard on R-1 only), section type, drug, source tier, license tag, version/effective date; **superseded versions excluded by default**.
- **Abstention:** calibrated score + margin gate per surface (reuse `abstain.py` machinery and ECE reporting).

### 4.5 Generation and verification upgrades
- **Claim-level support:** decompose each plan step / Q&A sentence into claims; require each claim to be supported by a cited span (lexical *and* an entailment check — small NLI model or LLM-judge calibrated on ≥100 human labels).
- **Numbers must match exactly:** any numeric token in an answer must appear verbatim in the cited span (guards "50 vs 500").
- **Answer modes:** `EXTRACTIVE` (default for R-3), `PLAN` (R-1). No free-form generative clinical advice.
- **Provider layer:** `LLMProvider` with Gemini, a local model (Ollama/llama.cpp, BACKLOG 7), and a recorded-cassette fake for CI. Apply real timeouts, bounded retries with jitter, model name from config, and token/cost/latency telemetry in every `TriageResponse`.

### 4.6 RAG-grounded rule mining (the bridge between "more rules" and "proper RAG")

```
 label chunk (Contraindications / Interactions / Populations)
        │  retrieve per catalogue entry (R-2 retrieval)
        ▼
 LLM proposes candidate rule JSON  +  verbatim supporting quote(s)
        ▼
 DETERMINISTIC VALIDATORS (no LLM):
   • quote is an exact substring of the cited chunk (hash-checked)
   • every number in the rule appears in the quote
   • drug/class ids exist in registry; severity ∈ taxonomy; schema v2 valid
   • rule not a duplicate of an existing rule (semantic key)
        ▼
 data/rules_candidates/*.yaml   status = CANDIDATE → SOURCED_UNREVIEWED (auto, if validators pass)
        ▼
 Review queue (UI or CLI): human accepts / edits / rejects  →  VERIFIED (reviewer id + date)
```

Why this is strong: it is a real RAG application with a **measurable** outcome (mining precision/recall against a hand-written gold set of ~30 rules), it scales the rule DB credibly (rules arrive *with* evidence), and it preserves your core safety rule — the LLM proposes, deterministic code validates, a human verifies. `SOURCED_UNREVIEWED` rules may run in demo mode and are badged; only `VERIFIED` rules count toward the headline coverage number.

### 4.7 Evaluation program (what to measure, and how it must be built)

**Benchmark v2 construction rules**
1. **No oracle track:** queries do **not** receive the syndrome; the retriever must find the right documents in the whole corpus. Keep the oracle-routed track only as a labelled secondary track.
2. **k below candidate-set size** or open-corpus retrieval so a shuffle cannot score full marks.
3. **Split by document (and by drug for labels)**, not by query; freeze with a content-hash lock file.
4. **Human-written queries:** ≥300, ≥30 Hinglish/abbreviated; written by teammates and, if possible, one clinician. Double-annotate ≥100 relevance judgments; report Cohen's κ.
5. **Hard negatives:** adult↔paediatric versions, superseded versions, same-drug-different-section, near-duplicate synthetic protocols, poisoned chunks (you have 6; grow).
6. **Validity self-test (CI gate):** random-order baseline must score below a stated bar (e.g., Recall@5 < 0.6, MRR < 0.4); if not, the benchmark is declared invalid.

**Metrics**
- Retrieval: Recall@{1,3,5,10}, MRR@10, nDCG@10, per family; abstention precision/recall at the calibrated threshold; ECE (observational); latency p50/p95 vs corpus size.
- Generation: claim-level citation precision/recall, faithfulness, numeric exact-match, unsafe-approval count (must be 0), repair success rate, abstention appropriateness.
- End-to-end: BLOCK leakage (must be 0 across arms C), time-to-verdict, cost per case.

**Arms (attribute errors correctly):** random · BM25 · dense · hybrid · hybrid+rerank · +contextual headers · +query rewriting · **no-retrieval** · **oracle-retrieval** (gold chunks given). Oracle vs real isolates retrieval error from generation error.

**Real-LLM ablation:** ≥3 models (e.g., one Gemini, one local, one other provider you have access to), ≥150 cases, temperature 0, paired bootstrap CIs, pre-registered decision rule (keep your `decide_backend()` pattern).

**Publishable plots (great README/portfolio material):** (1) Recall@k vs corpus size for BM25/dense/hybrid; (2) abstention PR curve; (3) rule count vs verified fraction over time; (4) unsafe-approval rate by arm and model with CIs; (5) citation precision vs overlap threshold; (6) p95 latency vs corpus size.

### 4.8 Making RAG visible in the UI
- **Evidence page v2:** query → filters applied → candidate list with BM25 / dense / fused / rerank scores and **rank-change arrows** → chunk viewer with the cited span highlighted → abstain reasons. A live **backend toggle** (BM25 / dense / hybrid / +rerank) so a viewer can *see* the difference on the same query.
